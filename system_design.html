1. ภาพรวม

ToDoList AI เป็น service หลัง Backend ของระบบ ToDoList ทำหน้าที่ "สมอง" ภาษาธรรมชาติ: เข้าใจคำสั่งงานจากแชต LINE, ถอดเสียงประชุม, สรุปงานใน LINE group และปรับน้ำเสียงข้อความแจ้งเตือน ไม่เป็นเจ้าของข้อมูลงาน — Backend เป็นผู้บันทึกงานจริง service นี้คืน draft + สถานะให้ Backend ตัดสินใจ

sync/chat
LLM agent + tools สร้าง/แก้/ค้นงาน, จัดการโปรเจกต์/ไฟล์
async/multi-channel
VAD → ASR → task + MoM → callback
async/line-group-summary/runs
batch สรุปงานจาก LINE group 3 รอบ/วัน
sync/api/message/persona
rewrite ข้อความเป็นน้ำเสียงเลขา + guard

10. Non-functional

ด้านวิธีที่ใช้
SecurityBearer token inbound (compare_digest, 401/403), x-internal-token outbound, secrets จาก AWS Secrets Manager, actor inject จาก state (model ปลอม id ไม่ได้), จำกัดการมอบหมายตาม BU/แผนก/level, tool result ดิบเป็น private
ReliabilityBackend API timeout 3s + retry 1 (transient), LLM router retry 2, STT retry 429/503 สูงสุด 10 ครั้ง, edit model retry 1 ครั้งเมื่อ output ไม่ผ่าน, persona fallback เป็นข้อความเดิม, group summary ใช้ผลเก่าซ้ำ + per-group isolation
CorrectnessPydantic schema ทุก boundary, protected fields + masking task_code, deterministic status, confirm เฉพาะจาก review
Scalability/chat stateless (state อยู่ Redis) scale แนวนอนได้; speech/group summary เป็น in-process background (จำกัดด้วย semaphore/lock)
Memoryดาวน์โหลดเสียงทีละไฟล์ (ออกแบบสำหรับ container ~512MB), ลบ tmp หลังจบ
ObservabilityLangfuse trace ต่อ request/job, usage+cost ใน response, log ต่อ job_id/batch_id
CompatibilityChatTask เก็บ field ที่ไม่รู้จัก, รับ payload legacy (project_name, assignee string, status ตัวเล็ก), flag ปิด = payload เดิม byte-identical

11. Design decisions

การตัดสินใจเหตุผลTrade-off
Unified agent เดียว (ไม่มี router model)ลด latency/cost, context เดียวต่อ turnprompt ใหญ่, ต้องมี probe วัด routing
Metadata เดินทางไปกลับกับ Backend + RedisBackend เห็นสถานะ draft และเป็นเจ้าของการบันทึกต้องรักษา contract อย่างเคร่งครัด
Deterministic status หลัง LLMกัน model ยืนยัน/ส่งงานเองโค้ด validation เยอะ
ถามยืนยันโปรเจกต์ทุกครั้งกันแนบโปรเจกต์ผิดเงียบ ๆเพิ่ม 1 turn
2 lanes สำหรับ speechLINE voice ไม่ต้องรอประชุมยาวยังไม่ durable
Feature flag ทุก behavior ที่ต้องรอ Backenddeploy ได้ก่อน Backend พร้อมต้องทดสอบทั้ง flag on/off
Persona guard แบบ token presenceไม่ส่งข้อความที่ fact ผิดfallback ~10%, ชื่อคนป้องกันด้วย prompt เท่านั้น

12. ข้อจำกัด & แผน

  • Background job ไม่ durable — /multi-channel และ group summary อยู่ในคิว in-process; container restart = หาย → แผน: durable queue (เช่น SQS) แยกตาม SLO
  • /line, /zoom เป็น stub
  • Persona fallback ยังสูงกว่าเป้า 10%
  • Backend ต้องพร้อมก่อนเปิด PERSONAL_TASK_ENABLED / TASK_TYPE_BY_PROJECT_ENABLED
  • Group summary ไม่มี grace period ที่ขอบรอบ, ประมวลผล group ทีละตัว
  • แผน: §4.7 ปรับคำสั่งเชิงลบเป็นภาษาทางการ (tone_adjusted)
